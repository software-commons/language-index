# Trusted Codex technical review

Language Index uses protected pull requests and a singleton merge queue. Active production ruleset `27874363` requires the Codex technical review check from Software Commons App `5893334`, along with SCES and Registry checks from GitHub Actions. SCES governs scientific verification of exact claim revisions. Publication requires separate authorization of the frozen commit and artifact digests. [Production ruleset](https://github.com/software-commons/language-index/rules/27874363) · [Publication control](PUBLICATION.md)

## Issuer and trust boundary

[The issuer patch](../research/review/shared-issuer.patch) adapts the shared License Index issuer at `24e5858889c7081be86149cb6cc431c665a2a4c0`. Use that exact revision on the organization-controlled deployment host. The adapter SHA-256 is `9390ac72d453f35204f631e224fbb1b70369d86d499ccb0530e53c27bd9707e3`. Keep the issuer code, configuration, audit records, GitHub credentials, and App private key beyond the reach of pull-request code and the reviewer identity. [Shared issuer commissioning](https://github.com/software-commons/license-index/blob/24e5858889c7081be86149cb6cc431c665a2a4c0/docs/CODEX_GATE.md)

Approval has two phases. Queue admission reviews the exact GitHub test merge and publishes a check to the single-parent PR head. That result only admits the PR to the mandatory queue. Final review binds a separate decision to the live singleton merge-group commit. The issuer checks the exact queue ref and ordered base and head parents, verifies successful SCES and Registry runs and job attempts on that commit, and fetches each required job's linked check by its exact ID. Each check must match the GitHub Actions App, workflow suite and merge commit. The issuer rechecks live protection, PR and queue evidence before posting. The review trace binds a fresh digest of the full patch and displays changed text, binary content, or mode changes as applicable. The issuer caps both review output streams while the process runs. Retained audit evidence identifies both decisions, reviewed commits, policy artifacts, and source checks.

Before a same-commit re-review, the denial-only path authenticates the exact pull request head or live singleton merge-group commit. The issuer uses a repository-scoped App token for check updates. Explicit head-only revocation can block an earlier passing admission check while the pull request is a draft or GitHub has yet to establish a test merge. The issuer checks the exact open pull request head and its single-parent Git commit before changing the status. When the request pins a test merge, the issuer verifies the live Git merge ref and its ordered base and head parents. It rechecks that exact ref and merge tree immediately before updating a check. Positive admission with a pinned head requires both exact pins. For an unpinned admission rerun, the issuer verifies the current Git head and clears any earlier passing checks before asking GitHub for an eligible test merge. Explicit merge-queue revocation authenticates the open pull request's base and head and the live queue ref with its ordered Git parents. It can update the exact queued check while GitHub prepares the ordinary test merge. Successful queue review still requires the eligible test merge and completed CI. It reads every page of the exact review check's history for that commit across the configured App's check suites and checks each prior passing result against the App, check context, and commit. GitHub treats `success`, `neutral`, and `skipped` as passing for required checks. The issuer archives the earlier receipts and changes those results to blocking failures. When no passing check exists, it records the exact Git target and confirms the check history again without reading an App token. This path remains available when live branch rules no longer meet the requirements for issuing a success. An earlier passing check with a missing or malformed decision digest can still be revoked once the App, check context, commit, and check ID match. A new success requires a decision digest and compatible live protections, commissioning policy, owner authorization where applicable, valid CI, and qualified evidence. Once the issuer has authenticated the exact revocation target and cleared earlier passing checks, a failed or inconclusive rerun leaves that check blocked. If an explicit pin fails verification, the issuer stops before updating any check. For admission, an operator can use a separate head-only denial request with the exact live head. [GitHub required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

When a candidate has an active SCES publication, the shared issuer stages the exact selection, qualification report, payload, and the selected records and evidence they depend on, including inherited material. It scans the candidate and frozen source registries independently in bounded batches to determine the required inputs. The issuer allows up to 256 MiB of registry processing and tracks a 300-second traversal deadline. Retrieving missing frozen records has its own limits of 64 MiB and 256 requests. Each Git call has its own timeout. The 16 MiB cap counts staged evidence bytes after Git transport framing is removed. It compares the membership and exact bytes of those inputs and binds the staged file digests to the review decision. Every publication transition preserves the inherited release artifacts and withdrawal advisories from the verified pull request base. A successor retains that base's dataset and links directly to its active qualification. The issuer checks that each archived qualification it relies on binds the exact claims payload. A withdrawal carries the exact base qualification forward and adds an advisory for that release. The issuer stages the former selection from the verified base, the preserved qualification, and the withdrawal advisory. Before reactivation, the issuer reads one archived release at a time and verifies its qualification, claims payload and matching withdrawal advisory against the verified inactive base. It then derives the required predecessor from the unique tip of the same dataset's checked qualification history. For every selected claim and premise, both verification records must bind the exact claim bytes. Each execution must complete at or after its start and by the captured UTC time. Research must finish by the time independent review starts. The two runs must have distinct execution IDs and traces, and their acquisition captures must be disjoint. The review trace must include fresh byte proofs for the staged files. Scientific verification and authorization to release are separate requirements. Changes to workflow, schema, testing, validation or other control paths require separate authorization for the commit reviewed in each phase.

When a change removes the active publication selection, pinned SCES-1.0 requires `require(set(reports) <= withdrawn, "unadvised-withdrawal", selection_path)`. If any retained qualification lacks an advisory, the transition to an inactive publication is blocked. Each advisory requires a substantiated reason. A qualified active successor can still proceed while earlier qualifications remain archived without advisories. Changing the withdrawal requirement requires a separate SCES revision. [Pinned SCES-1.0 validator](https://github.com/software-commons/.github/blob/ab26f278422772f2d9e5d4dd016407d14372a710/tools/sces/validate.py#L741-L748)

PR #6 introduces a separate Registry tests worker in the Domain workflow. The split layout takes effect on `main` when that change merges. Both workers install SCES dependencies from the pinned policy checkout using isolated Python. The issuer binds the Domain workflow blob to the exact reviewed merge-group commit. Only the pinned legacy workflow uses a single Registry validation job. Other revisions require successful Registry tests and Registry validation on the same exact Actions attempt. The final gate preserves the two required contexts and their GitHub Actions source, currently App ID `15368`. [Workflow change](https://github.com/software-commons/language-index/pull/6)

On Linux, keep the bubblewrap helper in a trusted runtime path. The review profile grants read access to the exact pinned executable and staged inputs alongside its minimal runtime paths. Make the issuer's validated GitHub CLI available with owner-readable rulesets and bypass actors. The issuer uses GitHub CLI only for GET requests. Test access isolation before issuing a live check. Configure the private issuer settings documented in the shared issuer, including `repository: software-commons/language-index`. Provide a short-lived repository-scoped installation token through the protected stdin provider. [Ruleset visibility](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset)
3. Rehearse the protected reviewer runtime using `--rehearsal-config` and verify the reviewer’s access boundaries. The production issuer pins `main` and `Software Commons / Codex technical review`. For an owner-authorized trial, independently review and pin a separate issuer copy to the trial branch and trial check context. Bind that trial context to its exact numeric App ID and configure a singleton merge queue for the trial branch. Require each check context once with its expected numeric source, strict status checks, and enforcement at ref creation. Both workflow callers subscribe to `merge_group`. Keep mandatory pull requests, existing approval requirements, deletion and force-push protection, and the empty bypass list throughout commissioning. [Singleton queue rule](../research/review/merge-queue-rule.json) · [Merge queue settings](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) · [Required check placement](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

Set the additional `authorized_cutover_ruleset` to the integer `27874363` only after the owner authorizes that ruleset's final cutover. 5. Run `python -B -m tools.review_gate review NUMBER --issuer-config CONFIG --queue-admission` using the appropriate pinned issuer copy. 6. Demonstrate the positive path and failure with missing or wrong-source decisions, new heads, base-only changes, retargeting, replaced queue refs or CI attempts, and reuse of a checked merge object. Preserve all branch protections and evidence. Dataset publication requires its own exact-artifact authorization.

## Continuous integration and branch cleanup

Start each new research or development segment from synchronized `main`. Keep the branch scoped to records, checks, documentation, and artifacts directly affected by that segment. Preserve exact source captures and independent scientific review. Validate against the actual protected base and open a focused PR to `main` as soon as the segment is ready. Use separately reviewable checkpoints when the full binary diff would exceed the shared issuer's 8 MiB capture limit.

Bind the authenticated technical review and required GitHub checks to the exact current PR and merge group. Merge eligible work through the protected workflow. Confirm the reviewed tree and frozen evidence ancestry on `main`. Research that is still provisional uses the corresponding registry state. Publication has a separate qualification and release authorization for exact assets. [Publication control](PUBLICATION.md)

After integration, compare every branch tip considered for cleanup with live `main`. Check that each exact tip and its required frozen source revisions are reachable. Record how any superseded PR’s unique evidence and historical reports reached `main`, then close the covered PR and remove only its contained remote and local branch. Prune remote tracking refs, synchronize the designated checkout, and verify a clean worktree before starting the next segment. Preserve any blocked branch with unique commits.
